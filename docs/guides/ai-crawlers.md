# AI crawlers and llms.txt

Set an AI crawler policy by purpose (training, search, user-triggered), generate robots.txt from it, and publish an llms.txt that describes every page.

Two generated files decide how AI systems meet your site. `robots.txt` says what they may do. `llms.txt` tells them what is there.

## Three decisions, not one

"Block AI" and "allow AI" are both too blunt, because AI crawlers do three different jobs:

| Purpose | What the crawler does | What you are deciding |
| --- | --- | --- |
| `training` | Collects pages to train models | Whether your writing becomes part of a model's general knowledge, without a link back |
| `search` | Builds the index an AI search product answers from | Whether you can be cited, with a link, when someone asks a related question |
| `user` | Fetches one page because a person asked an assistant about it | Whether an assistant can read your page when a user points it there |

Many sites want different answers. A publisher might refuse training and welcome search. A developer tool usually wants all three, because being known to the model is distribution.

```yaml
# gtm/gtm.yaml
crawlers:
  disallow: [/api/]
  ai:
    training: disallow
    search: allow
    user: allow
```

All three default to `allow`.

## What gets generated

```txt
# Generated by gtm-toolkit from gtm/gtm.yaml. Edit the spec, then run `gtm build`.

User-agent: *
Allow: /
Disallow: /api/

# AI crawlers, model training: disallow
# AI crawlers, AI search indexing: allow
# AI crawlers, user-triggered fetches: allow
# Allowed under the rules above:
#   OAI-SearchBot, Claude-SearchBot, PerplexityBot, DuckAssistBot, ChatGPT-User
#   Claude-User, Perplexity-User, meta-externalfetcher, MistralAI-User

User-agent: GPTBot
User-agent: ClaudeBot
User-agent: Google-Extended
User-agent: Applebot-Extended
User-agent: CCBot
User-agent: Bytespider
User-agent: meta-externalagent
User-agent: Amazonbot
Disallow: /

Sitemap: https://www.acme.dev/sitemap.xml
```

Two details are deliberate.

Allowed crawlers get no group of their own. In `robots.txt`, a crawler follows the most specific group that names it and ignores the rest. A group saying `User-agent: OAI-SearchBot` and `Allow: /` would release that bot from the `Disallow: /api/` that applies to everyone else. Listing allowed agents in a comment keeps them under the general rules.

There is no `Crawl-delay` and no blanket disallow of framework folders. Blocking a path such as `/_next/` hides your scripts and styles from the crawlers that render pages, and blocking `/api/` wholesale can hide the images your social cards are served from. Disallow specific paths, and check what they contain first.

The agents in each group are listed in the [crawler reference](../reference/crawlers.md).

## One agent at a time

```yaml
crawlers:
  ai:
    training: disallow
  agents:
    GPTBot: allow          # exception to the training rule
    SomeNewBot: disallow   # an agent the toolkit does not know yet
```

## What robots.txt cannot do

It is a published request. Well-behaved crawlers follow it. It does not stop a crawler that ignores it, and operators say plainly that user-triggered fetchers may not consult it, since a person asked for the page. If content must not be read, put it behind authentication.

## llms.txt

`llms.txt` follows the [llmstxt.org](https://llmstxt.org) proposal: a Markdown file at the root of the site that gives a language model a map.

```md
# Acme

> Acme makes deploy previews for data pipelines.

Acme gives every pull request that touches a pipeline its own isolated copy of the data, so reviewers see results before merge.

Not to be confused with:

- Not a data catalog or an observability tool. It runs before merge, not after.

## Pages

- [Pricing](https://www.acme.dev/pricing): Plans and limits.

## Blog

- [How to test a dbt change against production data](https://www.acme.dev/blog/2026-02-01-testing-dbt): Three ways to run a dbt change on real data before merge, what each costs, and where a deploy preview fits.
```

It is assembled from parts you already wrote:

- The H1 and the summary come from `site.name` and `site.description`.
- The paragraph and "Not to be confused with" come from `positioning.oneLiner` and `positioning.notThis`.
- "Pages" lists the routes that have a `title`.
- Each collection becomes a section, named by its `label`. Articles are ordered newest first. Every link carries the page's description.

That last point is why `seo/description` is an error by default. In `llms.txt`, the description is the one sentence a model reads before deciding whether to fetch the page.

Whether models use `llms.txt` varies by vendor and is still settling. The cost of publishing one is a generated file, and the content it needs, a clear statement of what you are and a described index of your pages, is worth having regardless.

## Checking the result

```bash
npx gtm build --dry-run   # what would change
npx gtm build             # write it
```

Then read both files. They are short, and they are the first thing a machine learns about you.
